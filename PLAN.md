# Plugin recap for OpenCode

## Goal

A session recap for OpenCode, modelled on Claude Code's recap. When you return to a session you get a short summary of where things stand, what was decided, and what is next. Generated by a small free model, always the same one, so it costs nothing and works for every OpenCode user out of the box.

## Shape

An OpenCode V2 plugin, repo `~/repos/opencode-recap`, published as `opencode-plugin-recap` on npm and loaded through `plugins` in `opencode.json(c)`. Everything needed exists in the plugin API, no core changes required.

## Model

The recap runs on the session's own model, resolved at recap time. No pinning, no fallback. If the model refuses a plugin issued generate call (OpenCode's free tier only serves the interactive client), no recap is produced.

The original pick was `opencode/big-pickle`, then a pinned Fireworks flash model. Testing showed OpenCode's free tier rejects plugin generate calls while credentialed providers accept them, and the user opted for session model resolution over pinning.

## Features

### 1. `/recap` command (MVP)

1. Register with `ctx.command.transform`, name `recap`.
2. In `execute`, read the transcript with `ctx.session.context({ sessionID })`.
3. Reduce the transcript to a digest (see Transcript handling).
4. Call `ctx.generate.text({ model: { providerID: "opencode", id: "big-pickle" }, prompt })`. This runs outside the session, adds nothing to history, and uses no tools.
5. Post the result back into the session with `ctx.session.synthetic({ sessionID, text })` so it is visible in the TUI and persisted.

### 2. Automatic recap on idle

1. Subscribe to the event stream with `ctx.event.subscribe`, watch for session idle/status events.
2. Debounce per session (for example 30 seconds of quiet) so a recap is not regenerated mid flow.
3. Generate the recap as above and store it in `ctx.storage` keyed by session ID, with the message count it covers.
4. Regenerate only when the message count has grown since the stored recap.

### 3. Recap on resume

1. When a stored recap exists and the session receives its first new prompt after being idle, inject the recap ahead of it as a synthetic message, or prepend it in the `prompt` hook as context ("Recap of this session so far: ...").
2. This mirrors Claude Code showing a recap when you resume a conversation.

### 4. Configuration

Plugin options in `opencode.json(c)`.

```jsonc
{
  "plugins": [
    {
      "package": "opencode-plugin-recap",
      "options": {
        "model": { "providerID": "opencode", "id": "big-pickle" },
        "auto": true,
        "injectOnResume": true
      }
    }
  ]
}
```

## Recap prompt

Fixed template, instructing the model to output five short sections.

1. Goal, what the user is trying to do.
2. Progress, what is done.
3. Decisions, anything agreed or ruled out.
4. State, files touched, commands run, current branch.
5. Next steps, the immediate next actions.

Cap output at roughly 300 words.

## Transcript handling

- Drop tool result bodies over a size threshold (keep the tool name and first lines).
- Skip system and synthetic messages.
- If the digest still exceeds a token budget, keep the first user message (the goal) plus the most recent N messages, and note the elision.

## Testing

1. Load locally with `"plugins": ["./src"]` or a `file:` path in a test project's `opencode.jsonc`.
2. Run a session with real tool use, invoke `/recap`, check the synthetic message appears.
3. Leave a session idle, confirm a recap lands in storage and regenerates only after new messages.
4. Resume the session, confirm the recap is injected once, not on every prompt.
5. Test with the model option pointed at a paid model to confirm the override path.

## Risks

- big-pickle capability is unknown for summarisation quality. Mitigation is the model option, and validating quality early in testing.
- Event names for idle need verification against the running server's event stream (`V2EventEncoded`). Check `opencode api get /openapi.json` or the event docs before implementing auto recap.
- Prompt hook injection runs once per admission; the resume injection must be idempotent per session to avoid stacking recaps.
